# 代码导读：llm-service 是怎么长出来的

这份文档不是 API 说明，是**学习路线**。目标是让你看完之后，
不但知道每个文件在干什么，还知道**当时为什么这么决定**。

项目现在有两条线：

- **W1（9/20–9/24）**：一个 FastAPI 的 LLM 服务 —— 流式、降级、能报成本。
- **W2（9/24–9/25）**：一条完整的 RAG 链路 —— 语料、分块、向量、混合检索、生成、评测。

两条线共用同一个地基（`llm.py`），W2 是长在 W1 上面的。

## 一、先建立一张地图

```
用户请求
   │
   ▼
中间件层（可观测，与业务无关）
   ├─ CostHeaderMiddleware  给响应加 X-Cost-CNY / X-Tokens-*   ← 9/24
   ├─ TrafficLogMiddleware  把每次请求与响应落盘              ← 9/22
   └─ RequestIdMiddleware   给每次请求编个号                   ← 9/20
   │
   ▼
路由层（main.py，只有三行：接参数 → 调函数 → 返回）
   │
   ├────────────── LLM 线（W1）──────────────┐
   ▼                                          │
业务层                                        │
   ├─ completion.py  结构化输出与自修复        │
   ├─ agent.py       工具调用循环              │
   ├─ streaming.py   流式版本                  │
   ├─ batch.py       并发版本                  │
   └─ resilience.py  重试与降级                │
                                               │
   ├────────────── RAG 线（W2）──────────────┘
   ▼
检索层  app/retrieval/（970 行，9 个文件含 __init__.py）
   ├─ embedding.py   三个 embedding 后端，统一入口 embed()      ← 9/25
   ├─ tokenize.py    中英混排分词，保住 API 文档里的标识符
   ├─ bm25.py        关键词检索
   ├─ hybrid.py      RRF 融合
   ├─ rerank.py      精排（identity 基线 + LLM）
   ├─ store.py       向量库封装：进程内单例 + small-to-big
   ├─ pipeline.py    四种模式可切换
   └─ schemas.py
   │
   ▼
生成层  app/rag/（380 行，5 个文件）
   ├─ prompts.py     三段约束：标编号 / 不许夹带 / 给退路
   ├─ abstain.py     两道拒答闸门 + 阈值校准依据 + 引用校验
   ├─ pipeline.py    六步链路
   └─ schemas.py
   │
   ▼
调用层（llm.py）—— 唯一真正发 HTTP 的地方
   │
   ▼
支撑层
   ├─ cost.py      账本
   ├─ pricing.py   价格与盈亏平衡
   └─ prompts.py   提示词装配（W1 的，别和 app/rag/prompts.py 搞混）
```

**关键结构特征一：`llm.py` 是唯一发 HTTP 的地方。**
这条不是洁癖，是生存需要——如果每个文件都自己发请求，那么
"换 provider""加重试""记账""改超时"这四件事你都得改八遍。
W2 的 rerank 也调 LLM，走的还是这一个口子。

**关键结构特征二：离线与在线分开。**
`scripts/` 是离线的数据准备层（抓语料 → 解析 → 切块 → 批量向量化 → 评测），
跑一次出个产物就完事。`app/` 是在线服务层，要长期跑着。
**生产代码反过来 `import scripts/` 是依赖倒置** ——
所以 embedding 客户端在 W2D5 从 `scripts/embed_corpus.py` 下沉到了
`app/retrieval/embedding.py`，离线脚本改成从它 import。

## 三、W1 的九个「为什么这么设计」

### 1. 为什么调用层只用标准库 urllib，不用 SDK

少一个 SDK 依赖，就少一处版本地雷。而且 OpenAI 兼容协议的请求体
本来就是个普通 JSON，没必要为此引入一整个包。
代价是重试、流式要自己写——但这两块恰恰是你必须懂的东西。

### 2. 为什么 `LLMError` 要带 `retryable` 字段

因为「该不该重试」这个判断**必须发生在离错误最近的地方**。
401 密钥错和 429 限流，从调用方看都是「抛了个异常」，
但一个重试一万次也没用，一个等一会儿就好。
把这个区分放在 message 字符串里让人去 grep，迟早会写错。

### 3. 为什么结构化输出失败要「喂回错误」而不是「重新生成」

重新生成，模型不知道自己上次错在哪，很可能再犯。
喂回错误，它看到了"上次那个输出，confidence 超范围了"，下一次就知道收敛。
**跟人改代码一个道理：看到报错再改，比凭感觉重写快。**

### 4. 为什么 `ok=False` 而不是抛异常

「调用成功了但输出不合规」和「调用失败了」是两件事：
- 调用失败 → HTTP 502，客户端该重试
- 输出不合规 → HTTP 200 但 `ok=False`，客户端该去改提示词

混为一谈，你会把「提示词写得烂」误判成「服务不稳定」。

### 5. 为什么 `dispatch()` 返回 error 字符串而不是抛异常

因为这些「失败」本质不是程序错误，是**模型的一次错误尝试**。
程序错误该崩；模型出错该被告诉它错在哪，让它改。
实测：模型调了不存在的 `get_weather_forecast`，收到错误消息后
第二轮自己改成了 `get_current_weather`。

### 6. 为什么循环要设 `max_turns` 而不是「直到它不调工具」

因为后者的终止条件**不由你控制**。模型可能反复调同一个工具、
可能一直重试一个失败的工具、可能陷入「查→不满意→再查」。
每一种都会烧钱到超时。所以终止条件必须是你设的上限——
模型的意愿只能作为"提前结束"的理由，不能作为"继续执行"的理由。

### 7. 为什么 tool 消息必须紧跟 assistant 消息、id 一一对应

因为 tool 消息要用 `tool_call_id` 指回具体哪一次调用。
所以带有 `tool_calls` 的那条 assistant 消息**必须原样留在列表里**，
哪怕它的 `content` 是空的——丢了它，后面的结果就无处安放。

### 8. 为什么成本放响应头而不是只在响应体

响应体是业务数据，格式各不相同；响应头是统一的观测面。
放在头里，浏览器 Network、curl、Nginx 日志都能直接看到，
而且能被网关直接采集做成本监控，不用解析业务 JSON。

> 实现时踩的坑：ASGI 的 headers 只能在 `http.response.start` 里发，
> `http.response.body` 消息**不带 headers 字段**。所以必须扣住 start 消息、
> 缓冲完 body、算完成本补头，再按 start → body 顺序发出去。

### 9. 为什么并发要用 `asyncio.to_thread` 而不是换异步 HTTP 客户端

瓶颈是网络等待，不是 CPU。把阻塞的 urllib 调用丢进线程池就够了，
省掉一整个 SDK 依赖和它的版本地雷。
**但必须加信号量**——不给上限的 `gather` 等于有多少发多少，
直接把对方限流打爆，然后你得到一堆 429，还以为是对面不行。

## 四、W2 的九个「为什么这么设计」

### 1. 为什么 embedding 客户端在 `app/` 而不是留在 `scripts/`

线上服务要用它把用户的问题向量化。生产代码反过来 `import scripts/`
是依赖倒置，部署时还得把一堆用不上的脚本打包进去。

而且**统一入口 `embed()` 是硬要求**：别在业务代码里写
`if backend == "local" ... else ...`。漏改一处就会变成
"库用一个模型、查询用另一个模型" ——
这种错**不报错、跑得起来、只是结果全错**，极难排查。

### 2. 为什么检索用暴力全量，不上 ANN 索引

实测：3563 条 × 1024 维，暴力只要 **0.24 ms**、召回 100%。
唯一比它快的是 IVF(nprobe=1) 的 0.12 ms，但召回掉到 0.657（丢 34%）。
Milvus HNSW 要 291 ms。

规模曲线约 0.04 ms/千条 → 10 万条 6.7 ms 仍够用，100 万条 67 ms 才需要 ANN。
**别为了"显得高级"提前上索引，那是负优化。**

### 3. 为什么融合用 RRF 而不是加权分数

`0.7 × 余弦 + 0.3 × BM25` 看着最直觉，但是错的：
余弦 ∈ [-1,1]（本语料实际 0.3~0.8），BM25 是 IDF 累加、无上界（实测 0~40）。
把 0.5 和 88 加在一起，权重根本不表示你以为的意思。

RRF（`Σ 1/(60+名次)`）**只看排名不看分数**，量纲问题直接消失，零调参。
**少一个要调的超参，就少一处过拟合。**

### 4. 为什么分词自己写而不用 jieba

语料是 API 文档，正文塞满了 `embedding-3`、`tokenizer_config.json`、
`/files/:file_id`。通用分词器会把它们切碎，而恰恰是这些词最关键——
把 `embedding-3` 切成 `embedding`/`3`，BM25 就再也比不过到处都是的"3"。

两条规则：英数标识符整体保留；中文**同时出 unigram 和 bigram**
（只用 bigram 两字查询失忆，只用 unigram 词序全丢）。

### 5. 为什么拒答要做成两道闸门

实测校准时发现：**命中组向量分 p50 = 0.775，未命中组 p50 = 0.749 —— 几乎一样。**
API 文档语料高度同质化，余弦**区分不了"像不像"和"能不能回答"**。

所以：
- 闸门①（检索侧，阈值 0.40）只挡跑题的 —— 域外问题 0.236~0.397 全拦下，**成本 0**
- 闸门②（生成侧，模型输出 NO_ANSWER）兜住域内但答非所问的

**两道都要有，不是设计癖好，是被数据逼出来的。**

### 6. 为什么拒答阈值用向量余弦而不是融合分

融合分（RRF）是 `1/(60+名次)` 的累加，取值范围只有 **0.016~0.033** ——
这么窄的区间根本选不出有意义的阈值，而且换个 k 值全部失效。

向量余弦是 0~1，语义直观："低于 0.35 就不答"谁都听得懂。

### 7. 为什么引用既要编号又要校验

- **编号**：不给编号，模型会写"根据文档所述"——看着有依据，实际没法验证。
- **校验**：只给 `citations` 而没有校验，"带引用"就只是装饰 ——
  模型完全可以编一个 `[3]` 出来而没人发现。
  校验能自动化那就必须做，它是**唯一能自动发现的幻觉信号**。

实测瞎标率 0/29。

### 8. 为什么 rerank 做成接口、带 identity 基线、失败即退化

- **做成接口**：rerank 是要被**开关**和**对比**的。
  关掉时必须存在一个"什么都不做"的实现当基线，
  否则你永远不知道 rerank 带来多少提升。
- **失败即退化**：解析不出来就保持原顺序，绝不抛异常。
  rerank 是增强环节不是主干，**不能让它把整个检索搞挂**。
- **候选池必须大于 topk**：只给 5 条让它重排 5 条，
  它没法把真答案从池外捞回来 ——
  **"rerank 没用"的误判往往就来自池子开太小。**

### 9. 为什么单例用 `lru_cache` 而不是全局变量

库 1.8 秒、BM25 1 秒，不能每个请求都来一遍。
用 `lru_cache` 的好处是它有 `.cache_clear()`，**测试里能干净地重置**，
全局变量做不到。

而且要**懒加载**：放在 import 阶段会让服务启动变慢，
而且库文件缺失会导致**服务直接起不来**。

## 五、W1 的四个实测踩坑

| 文件 | 坑 | 一句话 |
|---|---|---|
| `streaming.py` | usage 挂载位置 | DeepSeek 挂在带 `finish_reason` 的块上，OpenAI 是独立的空 choices 块。只在 choices 为空时取会全记成 0 |
| `streaming.py` | arguments 碎片 | `{"city"` / `: "杭州"` / `}` 分三块来，必须按 index 累加 |
| `cost_header.py` | ASGI headers | 只能在 start 消息里发，body 消息不带 |
| `tools.py` | sqlite 线程 | 模块导入时建的连接，FastAPI 会把同步路由丢进线程池 → 必须 `check_same_thread=False` |

**这四个坑的共同点：单元测试全绿也发现不了，只有真跑才暴露。**
这就是「看文档不算产出，跑通才算」这条规矩的由来。

## 六、W2 的十个实测踩坑

| 位置 | 坑 | 一句话 |
|---|---|---|
| `embed_corpus.py` | **向量库被覆盖** | 跑 `--limit 8` 试跑，`--out` 默认就是 `data/embed`，把 3700 块的库覆盖成 20 块。已加 `_guard_overwrite` 拒绝把大库覆盖成小库 |
| `scripts/vector_store.py` | **IVF 的 `self._mat` 没赋值** | `__init__` 里 `mat = _normalize(mat)` 是局部变量，search 里 `hasattr` 恒否 → 每次查询现场重建候选矩阵，加速比算成 0.3x，整张表作废 |
| `scripts/vector_store.py` | 自采样查询不加噪声 | 拿块自己的向量当查询，IVF 召回虚高到近 1.0，扫描没意义。已加 `perturb()` |
| `app/retrieval/` | Milvus 注册表是**进程级**的 | 换 db 文件没用，同进程第二次建同名 collection 报 already exists，索引同理 |
| `app/retrieval/` | `drop_collection` 被拦 | 本机安全删除钩子会 FAIL_CLOSED（Milvus 清 WAL 时）。改成从不 drop，名字带随机后缀 |
| `app/retrieval/` | 建 HNSW 的顺序 | `create_collection` 自带默认索引 → 直接 create_index 报"已存在"；已加载的不能 drop_index → 必须 load→release→drop→create→load |
| `app/retrieval/embedding.py` | **智谱额度耗尽** | 错误码 **1113 不是 429**，重建整库跑到第 59 批卡住。别把可用性押在一份免费额度上 |
| `app/retrieval/embedding.py` | 百炼单批上限 10 | 服务端硬校验，超过就 400。智谱能到 32 → 批次大小必须按后端分别设 |
| `scripts/run_baseline.py` | 忠实度把 `[1]` 当实体 | 引用编号被当成实体去原文匹配 → 每条答案**系统性低估**。修完 0.848 → 0.988 |
| `data/eval/golden.jsonl` | 语料里有垃圾块 | 想拿一个块当标准答案，打开是纯 CSS。golden set 建完必须逐条校验"块里真有答案" |

## 七、想改点什么练手？

### W1 的三个入口

1. **加一个工具** —— 改 `tools.py` 三处（`TOOL_SCHEMAS` / `ARG_MODELS` / `REGISTRY`），
   然后观察模型什么时候会调它、什么时候不该调它却调了。这是理解 schema 描述最快的方式。
2. **把 `max_turns` 改成 1** —— 看看两跳问题会怎么失败。理解熔断为什么必要。
3. **在 `pricing.py` 里加一个新模型的价格** —— 然后跑 `scripts/price_table.py`，
   看那张表怎么变。理解成本结构最快的方式。

### W2 的四个入口

4. **改 RRF 的 k** —— `app/retrieval/hybrid.py` 里把 60 改成 10 和 200，
   跑 `scripts/run_retrieval_eval.py` 看数字变不变。答案是"几乎不变"，
   亲眼看一次比读十篇文章有用。
5. **改拒答阈值** —— `app/rag/abstain.py` 里把 0.40 改成 0.20 和 0.60，
   跑 `scripts/run_rag_eval.py` 看拒答准确率怎么变。
   你会看到：调低了域外问题就漏，调高了域内问题就误拒。
6. **关掉 rerank 再打开** —— `scripts/run_retrieval_eval.py --rerank identity` vs `--rerank llm`。
   看它到底值不值那 3 倍延迟。注意多跑几次，它有随机性。
7. **给 golden set 加 5 条难例** —— 用 `scripts/expand_golden.py` 的格式，
   加几条"必须同时拿到两个来源"的题，再跑 `scripts/run_baseline.py`
   看跨文档全中率。这个数现在只有 0~25%，是当前最真实的弱点。

改完记得 `pytest -q`，现在有 **205 项测试**兜底（203 通过 + 2 跳过）。

## 八、文件清单速查

```
app/                          在线服务层（长期跑着）
  main.py                     路由，21 个端点，刻意写得很薄
  llm.py                      ★唯一发 HTTP 的地方
  config.py / schemas.py
  ── W1 ──
  completion.py  结构化输出与自修复
  tools.py / agent.py         工具与工具调用循环
  streaming.py / batch.py     流式与并发
  resilience.py               重试与降级
  pricing.py / cost.py / cost_header.py / traffic.py
  prompts.py                  W1 的提示词装配
  ── W2 ──
```
